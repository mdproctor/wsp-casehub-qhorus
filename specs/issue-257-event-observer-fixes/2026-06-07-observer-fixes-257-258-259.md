## #257 — Separate EVENT telemetry from content; fail-fast for application callers

### Problem

`MessageDispatch.Builder` accepts `.content(String)` for `MessageType.EVENT` without any guard. The content is silently nulled by `MessageObserverDispatcher` before delivery, so application observers receive `null`. No error surfaces at dispatch time — data disappears.

Separately, `LedgerWriteService.populateTelemetry()` extracts MCP tool telemetry (`tool_name`, `duration_ms`, `token_count`, `context_refs`, `source_entity`) by parsing `dispatch.content()` as JSON. This conflates the application-visible content field with an internal ledger concern, which is why content cannot be used for application-level EVENT payloads.

### Root cause of the coupling

`message.content` is the application layer. `MessageLedgerEntry.toolName` etc. are the ledger layer. Using the same field (`content`) to carry both is the architectural error. The proper fix is in `casehub-ledger#126`, which will move telemetry capture to a mechanism that does not touch `content`. This issue is the partial step: introduce an explicit `telemetry` field in `MessageDispatch`, route internal telemetry callers to it, and enforce that application callers cannot set `content` on EVENTs.

### Design

**Part A — Add `telemetry(String)` to `MessageDispatch`**

Add a 13th field `String telemetry` to the `MessageDispatch` record, after `deadline`. Add a corresponding `telemetry(String v)` setter to `Builder`. No validation on `telemetry` in `build()` — it is internal infrastructure, not consumer API.

`LedgerWriteService.populateTelemetry()` and `ReactiveeLedgerWriteService.populateTelemetry()` both change their parameter from `dispatch.content()` to `dispatch.telemetry()`. This is the decoupling: telemetry extraction reads from an explicit field, not from the application content field.

**Part B — Fail-fast guard in `Builder.build()`**

Add to the `switch` in `build()`:
```java
case EVENT -> {
    if (content != null)
        throw new IllegalArgumentException(
            "EVENT messages must not carry content — use STATUS for content-bearing observe-channel broadcasts.");
}
```

The reference to `casehub-ledger#126` belongs in Javadoc, not the runtime exception. Agents receive `ToolCallException` messages and do not benefit from cross-repo issue references.

**Part C — Update all 8 production EVENT callers**

| Caller | Change |
|--------|--------|
| `ChannelGateway.receiveHumanMessage()` | `.content(telemetryJson)` → `.telemetry(telemetryJson)` |
| `ChannelGateway.receiveObserverSignal()` | Remove `.content(signal.content())` — drop the payload; the EVENT record (sender, channelId, timestamp) is the observer signal |
| `QhorusMcpTools.force_release_channel` | Remove `.content(auditContent)` — the EVENT is the audit record |
| `QhorusMcpTools.delete_message` | Remove `.content(...)` |
| `QhorusMcpTools.clear_channel` | Remove `.content(...)` |
| `ReactiveQhorusMcpTools.force_release_channel` | Remove `.content(auditContent)` |
| `ReactiveQhorusMcpTools.delete_message` | Remove `.content(...)` |
| `ReactiveQhorusMcpTools.clear_channel` | Remove `.content(...)` |

The audit-text callers (`force_release`, `delete_message`, `clear_channel`) pass plain strings that `populateTelemetry()` already skips (not JSON). Dropping them loses nothing in the ledger and nothing meaningful in `message.content` — the tool sender, channel, and timestamp are the audit record.

**`MessageObserverDispatcher` nullification**

The ternary `message.messageType == MessageType.EVENT ? null : message.content` becomes dead code for all production paths: after Part B+C, no production EVENT dispatch can carry non-null content. The guard remains in place as defense-in-depth against direct `Message` entity construction that bypasses the `Builder`. Update the Javadoc to say this explicitly — do not reference `casehub-ledger#126` here, which is about telemetry storage decoupling, not about the nullification.

**`MessageReceivedEvent` compact constructor**

The `if (messageType == MessageType.EVENT && content != null) throw` guard remains. Update Javadoc: "content is null for EVENT because the Builder guard prevents non-null content from reaching the dispatcher. Pending casehub-ledger#126, which will remove this constraint once telemetry is fully decoupled from message content."

## #258 — ChannelSlugValidator: actionable error for dot-notation names

### Problem

`ChannelSlugValidator.validateSlugPath()` splits on `/`, so `quarkmind.scouting.intel` is one segment. The error repeats the full name as both the segment and the full name, and does not explain that dots are invalid or suggest any correction.

Current error:
```
Invalid channel name segment 'quarkmind.scouting.intel' — must match
[a-z][a-z0-9]*(-[a-z0-9]+)*. Full name: 'quarkmind.scouting.intel'
```

### Fix

After the existing `!SEGMENT_PATTERN.matcher(segment).matches()` check, branch on whether the segment contains `"."` (as `CharSequence`, not `char`). When a dot is found, generate a specific message:

```
Invalid channel name segment 'quarkmind.scouting.intel' in 'quarkmind.scouting.intel'
— dots are not valid segment characters ('/' is the qhorus path separator, not '.').
Suggested alternatives: 'quarkmind-scouting-intel' (hyphen) or 'quarkmind/scouting/intel' (hierarchy).
Segment must match [a-z][a-z0-9]*(-[a-z0-9]+)*.
```

The dot-to-hyphen and dot-to-slash suggestions are computed from the segment string, not hardcoded. For non-dot failures (uppercase, digit-start, trailing hyphen, etc.), the existing error format is retained — the new branch is strictly additive.

### Scope

- `ChannelSlugValidator.validateSlugPath()` — branch on `segment.contains(".")` after pattern mismatch, compute suggestions from segment
- Javadoc on `validateSlugPath()` — document that `/` is the path separator and dots are invalid

### Tests

- `quarkmind.scouting.intel` → error contains `quarkmind-scouting-intel` and `quarkmind/scouting/intel`
- `quarkmind/scouting.intel` (dot in a non-first segment) → first segment passes, second segment triggers dot-specific error
- `INVALID` (uppercase, non-dot failure) → existing generic error, no dot-specific hint
- `123-invalid` (digit-start, non-dot) → existing error format
- `valid/path/name` → passes validation

## #259 — Add `@Any` to `Instance<MessageObserver>` injection

### Problem

Both `MessageService` and `ReactiveMessageService` inject `Instance<MessageObserver>` without `@Any`. CDI's unqualified `Instance<T>` resolves only beans with the `@Default` qualifier. Any `MessageObserver` implementation with an additional qualifier (`@Named`, a custom `@CaseType`, any application qualifier) is silently excluded from `observers.handles()`.

### Fix

```java
// Before
@Inject
Instance<MessageObserver> observers;

// After
@Inject @Any
Instance<MessageObserver> observers;
```

Applied identically in `MessageService` and `ReactiveMessageService`. CDI automatically adds `@Any` to every bean; `@Any Instance<T>` correctly discovers all beans implementing `T` regardless of additional qualifiers.

`InProcessMessageBus` (`@DefaultBean`) retains `@Default` and continues to be discovered. The channel filter (`observer.channels()`) and scope field (`observer.scope()`) are applied after handle resolution — unaffected by this change.

Update `MessageObserver` Javadoc to state explicitly: "Implementations may carry additional CDI qualifiers (e.g. `@Named`, custom application qualifiers) — the dispatcher discovers all implementations regardless of qualifiers."

### Test

A `@QuarkusTest` with a custom-qualified `MessageObserver` implementation. The test qualifier annotation must be declared with:
```java
@Qualifier
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.FIELD, ElementType.METHOD, ElementType.PARAMETER})
```

Without `@Retention(RUNTIME)`, Arc will not see the qualifier at runtime.

The test dispatches a message and asserts the qualified observer's `onMessage` is called. A second assertion verifies that a qualified observer with a non-empty `channels()` filter receives only matching messages and is correctly excluded from others — confirming that channel filter and qualifier discovery compose correctly.

A separate reactive-path test is not needed: the CDI injection is resolved at augmentation time and shared by both stacks. One blocking-path test covers both.

## Coherence review

- **`MessageDispatch` is consumer-facing (api module).** Adding the `telemetry` field breaks the canonical constructor for any downstream consumer (`Claudony`, `casehub-engine`) that constructs `MessageDispatch` directly. That breakage is intentional — those callers must add `null` for `telemetry`. No downstream consumer legitimately sends EVENT with content today.
- **The fail-fast guard in `build()` is also a consumer-facing break** for any caller that sends `EVENT+content`. Correct — that is the point.
- **`@Any` on `Instance<MessageObserver>` is backwards-compatible** — existing default-qualified beans continue to be discovered.
- **PLATFORM.md `observe` channel semantics** (EVENT, QUERY, STATUS allowed) are unchanged. EVENT remains a signal type at the SPI boundary.
