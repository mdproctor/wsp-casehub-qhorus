## #257 — EVENT content must fail-fast at dispatch

### Problem

`MessageDispatch.Builder.content()` silently accepts a non-null payload for `MessageType.EVENT`. The content is then nulled by `MessageObserverDispatcher` before constructing `MessageReceivedEvent`, so observers always receive `null`. No error is raised at dispatch time — data simply disappears.

### Root cause (deferred to ledger)

`LedgerWriteService` extracts MCP tool telemetry (`tool_name`, `duration_ms`, `token_count`) from the `content` field of EVENT messages by JSON parsing. This couples the EVENT content field to a telemetry schema, forcing the dispatcher to null content so application observers don't receive raw internal telemetry blobs. The proper fix is to decouple telemetry capture from `message.content` in the ledger — tracked as `casehub-ledger#126`. Until that ships, EVENT is a content-free signal type at the consumer SPI boundary.

### Fix (this session)

Add a `case EVENT` branch to `MessageDispatch.Builder.build()` that throws `IllegalArgumentException` if `content != null`. The silent discard becomes a loud, immediate failure at the call site — before any dispatch, before any DB write.

Error message:
```
EVENT messages must not carry content — EVENT is a content-free signal. Use
MessageType.STATUS for content-carrying observe-channel broadcasts. This constraint
will be removed when casehub-ledger#126 decouples telemetry from EVENT content.
```

### Scope

- `MessageDispatch.Builder.build()` (api module) — add `case EVENT` guard
- `MessageReceivedEvent` compact constructor (api module) — existing guard remains as defense-in-depth; update Javadoc to reference ledger#126
- `MessageObserver` Javadoc — document the constraint and STATUS as the correct alternative
- `MessageObserverDispatcher` Javadoc — clarify why EVENT content is nulled (ledger coupling)

### Out of scope

Removing the nullification from `MessageObserverDispatcher`. That waits on `casehub-ledger#126`.

### Tests

- `MessageDispatch.Builder.build()` with `type=EVENT` and `content=non-null` → `IllegalArgumentException`
- `MessageDispatch.Builder.build()` with `type=EVENT` and `content=null` → builds successfully
- Existing tests for EVENT dispatch (ledger entries, observer calls with null content) must remain green

## #258 — ChannelSlugValidator: actionable error for dot-notation names

### Problem

`ChannelSlugValidator.validateSlugPath()` splits on `/` (the path separator), so `quarkmind.scouting.intel` is treated as a single segment. The current error repeats the full name in both the "segment" and "full name" positions, and does not explain that dots are invalid nor suggest a correct form.

Current error:
```
Invalid channel name segment 'quarkmind.scouting.intel' — must match
[a-z][a-z0-9]*(-[a-z0-9]+)*. Full name: 'quarkmind.scouting.intel'
```

### Fix

In `validateSlugPath()`, after the `SEGMENT_PATTERN` match fails, check whether the segment contains a dot. If it does, generate a dot-specific error that:
- Names the offending segment
- States explicitly that dots are not path separators in qhorus
- Suggests both alternatives: hyphens (`quarkmind-scouting-intel`) and slashes (`quarkmind/scouting/intel`)
- Includes the pattern for completeness

Error when dot detected:
```
Invalid channel name segment 'quarkmind.scouting.intel' in 'quarkmind.scouting.intel'
— dots are not valid segment characters (dots look like path separators but '/' is the
qhorus path separator). Use hyphens for compound names ('quarkmind-scouting-intel') or
slashes for path hierarchy ('quarkmind/scouting/intel').
Segment must match [a-z][a-z0-9]*(-[a-z0-9]+)*.
```

For non-dot failures, the existing error message format is retained (it is correct for other violations such as uppercase, digits at start, etc.).

### Scope

- `ChannelSlugValidator.validateSlugPath()` — branch on `segment.contains('.')` after pattern mismatch
- Javadoc on `validateSlugPath()` — document that dots are invalid and why
- No change to `SEGMENT_PATTERN` or validation logic

### Tests

- `quarkmind.scouting.intel` → error message contains both `quarkmind-scouting-intel` and `quarkmind/scouting/intel`
- `INVALID` (uppercase, non-dot failure) → existing error format, no dot-specific hint
- `valid/path/name` → passes validation
- `123-invalid` (digit start) → existing error format

## #259 — Add `@Any` to `Instance<MessageObserver>` injection

### Problem

`MessageService` and `ReactiveMessageService` both inject `Instance<MessageObserver>` without `@Any`. CDI's unqualified `Instance<T>` lookup resolves only beans with the `@Default` qualifier. Any `MessageObserver` implementation carrying an additional qualifier (e.g., `@Named`, a custom application qualifier) is silently excluded — it never receives messages.

### Fix

Add `@jakarta.enterprise.inject.Any` to both injection points:

```java
// MessageService
@Inject @Any
Instance<MessageObserver> observers;

// ReactiveMessageService
@Inject @Any
Instance<MessageObserver> observers;
```

`@Any` is automatically added by CDI to every bean. `@Any Instance<T>` discovers all beans implementing `T` regardless of other qualifiers — the correct semantics for a global broadcast SPI. Existing implementations (`InProcessMessageBus @DefaultBean`, etc.) are unaffected.

### Scope

- `MessageService` — add `@Any` import and annotation
- `ReactiveMessageService` — add `@Any` import and annotation
- `MessageObserver` Javadoc — note that qualified implementations are supported

### Tests

A `@QuarkusTest` that registers a `MessageObserver` bean with a custom qualifier (e.g., `@io.quarkus.test.common.QuarkusTestProfile`-scoped `@Alternative` with a qualifier annotation defined in `src/test/java`) and verifies `onMessage` is invoked after `messageService.dispatch()`. Must also confirm the channel filter (`observer.channels()`) still applies correctly for qualified observers.

## Coherence review

- All changes are internal to qhorus; no cross-repo API breaks.
- `MessageDispatch` is in the `api` module (consumer-facing) — the new `case EVENT` guard IS a breaking change for any consumer passing EVENT+content. That breakage is the point: it surfaces previously-silent data loss.
- `@Any` on `Instance<MessageObserver>` is backwards-compatible — existing default-qualified beans continue to be discovered.
- PLATFORM.md `observe` channel type table (`EVENT, QUERY, STATUS` allowed) is unaffected — the channel semantic is unchanged.
