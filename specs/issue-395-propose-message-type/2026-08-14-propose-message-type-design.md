# PROPOSE Message Type — Design Spec

**Issue:** casehubio/qhorus#395
**Date:** 2026-08-14
**Status:** Approved
**Decisions:** [decisions.md](decisions.md)
**Debate artifacts:** [explorations/D1-debate/](explorations/D1-debate/)

## Summary

Add `PROPOSE` as the 10th message type in qhorus's speech-act taxonomy — a commissive speech act for negotiation protocols. PROPOSE fills a genuine gap: STATUS (the ADR-0005 commissive) is actually an assertive (it extends existing obligations, it does not create conditional new ones). PROPOSE creates a conditional self-binding: "I will do X if you agree."

The key behavioral difference from COMMAND: RESPONSE on a PROPOSE commitment does **not** auto-fulfill. Only DONE (explicit acceptance) fulfills. This enables counter-proposal exchange without premature commitment closure.

## Theoretical basis

PROPOSE occupies a unique cell in the Searle-category × deontic-effect matrix:

| Searle category | Existing types | Deontic effect |
|---|---|---|
| Directive (epistemic) | QUERY | Creates receiver obligation to inform |
| Directive (action) | COMMAND | Creates receiver obligation to execute |
| Assertive | RESPONSE, DECLINE, STATUS | Commits to truth / extends obligation |
| **Commissive** | **PROPOSE** | **Conditional sender-obligation; receiver must respond** |
| Declaration | HANDOFF, DONE, FAILURE | Changes institutional reality |
| Perlocutionary | EVENT | No deontic footprint |

**Stopping criterion:** A new type is justified only when it occupies a unique cell in this matrix that no existing type covers. PROPOSE is the last type that passes this test. Future candidates must demonstrate an empty cell:

| Candidate | Why excluded |
|---|---|
| ACK | Lifecycle transition — handled by `acknowledgedAt` |
| APPROVE / VETO | HITL-specific — deferred to human-in-the-loop design |
| COUNTER-OFFER / BID / WITHDRAW | Within-category commissive refinements — handled by projection-layer semantics |

## Commitment model

PROPOSE uses the **same commitment direction** as COMMAND: `requester = sender (proposer)`, `obligor = target (receiver)`. The receiver must respond — accept, reject, delegate, or extend. This is not inverted.

The difference is in **fulfillment semantics**, not obligation direction:

| Incoming type | On COMMAND commitment | On PROPOSE commitment |
|---|---|---|
| RESPONSE | `fulfill()` | **No-op** (valid interaction, non-fulfilling) |
| DONE | `fulfill()` | `fulfill()` (acceptance) |
| DECLINE | `decline()` | `decline()` (rejection) |
| FAILURE | `fail()` | `fail()` |
| HANDOFF | `delegate()` | `delegate()` |
| STATUS | `acknowledge()` | `acknowledge()` |
| EVENT | No-op | No-op |

The existing 7-state lifecycle (OPEN → FULFILLED / DECLINED / FAILED / DELEGATED / EXPIRED) is unchanged. PROPOSE is a new entry point into the same state machine.

## Changes

### 1. MessageType.java (api)

Add `PROPOSE` enum value:

```java
/** Offer conditional commitment. Sender binds to action contingent on receiver's acceptance. Commissive. Carries correlation_id. */
PROPOSE;
```

Method implementations:

| Method | Returns | Rationale |
|---|---|---|
| `isAgentVisible()` | `true` | Proposals appear in agent context |
| `requiresCorrelationId()` | `true` | Auto-generated by infrastructure at MCP layer (same as COMMAND/QUERY); Builder.build() enforces non-null as a safety net; proposal without tracking is meaningless |
| `requiresContent()` | `true` | A proposal without terms is meaningless |
| `requiresTarget()` | `false` | Multilateral proposals target all participants |
| `isTerminal()` | `false` | Proposals are initiating, not terminal |

### 2. MessageDispatch.Builder.build() (api)

Add `case PROPOSE` to the validation switch:

- `correlationId` required — throws `IllegalArgumentException` if null (stricter than COMMAND, which falls through to default with no correlationId validation)
- `content` required — throws if null or blank
- `inReplyTo` optional — initial proposals don't reply to anything; counter-proposals might reference a prior proposal
- `target` optional — `requiresTarget() = false`

### 3. MessageService.dispatch() (runtime)

Three touch points:

**a) Commitment ID generation** (pre-switch guard, ~line 324):

```java
// Before:
final UUID commitmentId = (dispatch.correlationId() != null &&
    (dispatch.type() == MessageType.COMMAND || dispatch.type() == MessageType.QUERY))
    ? UUID.randomUUID() : null;

// After:
final UUID commitmentId = (dispatch.correlationId() != null &&
    (dispatch.type() == MessageType.COMMAND || dispatch.type() == MessageType.QUERY
     || dispatch.type() == MessageType.PROPOSE))
    ? UUID.randomUUID() : null;
```

**b) Commitment lifecycle switch** (~line 352):

```java
// Before:
case QUERY, COMMAND -> { /* open commitment */ }
case RESPONSE, DONE -> commitmentService.fulfill(dispatch.correlationId());

// After:
case QUERY, COMMAND, PROPOSE -> { /* open commitment */ }
case DONE -> commitmentService.fulfill(dispatch.correlationId());
case RESPONSE -> {
    // RESPONSE fulfills QUERY and COMMAND commitments but NOT PROPOSE commitments
    var commitment = commitmentStore.findByCorrelationId(dispatch.correlationId());
    if (commitment.isPresent() && commitment.get().messageType() != MessageType.PROPOSE) {
        commitmentService.fulfill(dispatch.correlationId());
    }
}
```

**c) Trust gate** (~line 191): No change. PROPOSE is not trust-gated. The `dispatch.type() == MessageType.COMMAND` guard remains as-is.

### 4. StoredMessageTypePolicy.validate() (runtime)

Add PROPOSE to hard-enforcement branch:

```java
// Before:
case COMMAND, QUERY -> { /* hard enforcement — throws */ }

// After:
case COMMAND, QUERY, PROPOSE -> { /* hard enforcement — throws */ }
```

PROPOSE creates commitments, so advisory-only enforcement would risk orphan commitments (per PP-20260604-a7ad99).

### 5. CorrelationIntegrityChecker (runtime)

Add PROPOSE resolution matching rules:

- RESPONSE on PROPOSE → **no advisory** (valid non-fulfilling interaction)
- DONE on PROPOSE → **no advisory** (acceptance)
- Existing obligor identity check works correctly: receiver (obligor) sends DONE/DECLINE/FAILURE, which matches `commitment.obligor()`

No special exemptions needed — the commitment direction is the same as COMMAND.

### 6. A2ATaskState (runtime)

No change needed. PROPOSE falls to `default -> 0` in `statePriority()` (priority 0 → "submitted"). PROPOSE is not terminal. Its commitment resolution uses existing types (DONE, DECLINE, FAILURE) which already have correct A2A mappings.

### 7. QhorusMcpTools (runtime)

Update `send_message` tool:
- Add `PROPOSE` to the type parameter documentation
- PROPOSE follows the same dispatch path as all other types

### 8. Notification bridge

Add `PROPOSED` to `QhorusObligationEvent.Kind` enum. `NotificationBridgeObserver` fires on PROPOSE dispatch (alongside existing COMMAND → ASSIGNED mapping). DONE-on-PROPOSE fires existing `FULFILLED` kind.

### 9. Examples — type-system module

## What this does NOT cover

Per the issue:
- **Withdrawal semantics** (proposer retracting their own proposal) — handled by blocks' metadata layer (`entryType=WITHDRAW` on a DECLINE)
- **Multi-issue negotiation** (proposals with multiple attributes/dimensions) — projection-level concern
- **Concession strategies** — consumer logic, not protocol infrastructure
- **LLM classification accuracy** for PROPOSE — empirical validation in `examples/agent-communication/` after implementation

## Test strategy

- **Unit tests:** MessageType method implementations, Builder validation (correlationId + content required, inReplyTo optional), StoredMessageTypePolicy hard-enforcement
- **CDI-free unit tests:** CorrelationIntegrityChecker resolution matching for PROPOSE
- **Integration tests:** Full dispatch lifecycle — PROPOSE → DONE (acceptance), PROPOSE → DECLINE (rejection), PROPOSE → RESPONSE (non-fulfillment verified), PROPOSE → FAILURE, PROPOSE → HANDOFF delegation
- **MessageTaxonomyTest:** Enum coverage in examples/type-system/
- **Notification bridge:** PROPOSED kind fires on PROPOSE dispatch
